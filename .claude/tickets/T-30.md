## Goal

Deploy `server` (ui-service) to Railway, remove CORS from the gateway (no longer needed —
all browser traffic goes through server, gateway only sees server-to-server calls),
and migrate CI/CD from GitHub Pages to Railway.

---

## Phase 1 — Railway service provisioning

**Owner actions required (cannot be done in code):**

1. Create new Railway service `server` from `Dockerfile.server`
2. Set environment variables:
   - `GATEWAY_URL` — internal Railway URL of the gateway service
   - `GATEWAY_ALLOWED_HOST` — hostname of gateway
   - `JWT_SECRET` — same value as used by gateway
   - `ASSET_VERSION` — e.g. `20260329`
   - `PORT` — Railway sets this automatically
3. Set custom domain if desired (or use Railway-generated URL)
4. Note the public URL of the new `server` service

---

## Phase 2 — CORS removal from gateway

**Why:** With `server` as the sole entry point for browsers, the gateway only
receives requests from `server` (server-to-server). Browser origin headers never
reach the gateway. The `CorsLayer` in `gateway/src/main.rs` is dead code.

**Changes:**
- Remove `CorsLayer` and `tower-http` CORS dependency from `gateway/src/main.rs`
- Remove `ALLOWED_ORIGINS` constant
- Remove `tower-http` cors feature if no longer used elsewhere

**Prerequisite:** `server` must be deployed and serving traffic before this change
is committed — otherwise removing CORS breaks the current GitHub Pages deployment.

## Phase 3 — CI/CD migration

**Requires explicit owner instruction before implementation.**

Current state: `deploy.yml` deploys to GitHub Pages.
Target state: `server` is deployed via Railway (auto-deploy on push to `dev` or `main`).

Actions (owner decides scope):
- Disable or remove GitHub Pages deploy workflow
- Confirm Railway auto-deploy is configured for the `server` service
- Update any status badge or README URLs pointing to GitHub Pages domain
