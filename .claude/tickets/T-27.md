## The Problem

During every implementation of a feature or a bug fix, Claude hallucinates new specs, uses shortcuts, add stubs,
avoids proper validation, removes guards, couples and de-couples code modules, changes the architecture, re-introduces previously fixed errors, and questions or ignores previous design decisions.
Claude wastes millions by running in circles. It's currently useless as a software developer.

The recent commits show that Claude adds, edits, removes code in circles. Often the added code doesn't compile, build or deploy processes fail. Examples:

- `autobuild` for rust: Claude added it without any need, without prior consultation and justification. CodeQL failed. Caude had to remove it.
- `X-Headers`: Claude added fields to the request headers during the implementation of the single source of truth `authority-service.rs`. The implementation introduced new bugs. Claude suggests to remove the recently added `X-Headers`.

## Proposed Solution

A detailed, concise, coherent, unambiguous Specifications Document (PRD) acts as enforcable source of truth for any and every file changing task. Missing specifications must be specified before the codebase or other files are edited.

For the entire project:

- its codebase (ui, middle layer, persistence),
- its infrastructure
- the interactive workflow between claude code, the project owner, ticket-, PR-, merging-, QA-management, bug reports, github actions ie. codeql, deployment)

define specifications based on the current situation and develop them into a coherent specification.

We have implicitly defined (to this date) the following:

### Programming languages

- ui: html5, javascript, css (bootstrap + bootstrap js), wasm (rust)
- middle layer services: rest, rust, crud (GET, POST, PUT, DELETE, PATCH)
- persistence: mongodb shell

### Architecture + Infrastructure

- ui: deployed to github pages, Jekyll SSG + Thymeleaf templating
- middle layer services: microservices deployed and hosted on railway.com (hobby tier)
- backend: mongodb deployed and hosted on railway.com

### Security

- Privacy-by design
- GDPR compliant (as-good-as-possible)
- data minimization (no localStorage, sessionStorage only if needed)
- encryption of all user relevant information on the backend
- E2EE, hashing, OPAQUE, JWT, ALLOWED_HOSTS

### Coding Style and Best Practices

- Modularizaton of javascript and rust libraries
- DRY, YAGNI

### Workflow

The workflow is currently defined by the following documents:

- `claude.md`, `tickets.md`, `session.md`
- Weekly CodeQL Analysis with Bug-Fix Session after the fetch of the analysis

The new workflow specification:

- MUST include fact checking steps for `claude code`
- MUST include handling of incomplete or ambiguous input from project owner
- MUST include harness strategies
- MUST include steps to include new specifications in case of a build, deploy error, CodeQL warning.
- SHOULD include a way to estimate token usage and reporting
- SHOULD include wrap-up mechanism before the token limit will be hit
- SHOULD aim at maximum automatization
  
## Instructions for the of the Specification Document

- You must first read this document and the this instructions and identify missing, wrong information. Only if this document is complete, specific, without errors
  you will start writing the Specification Document.
- You must develop the Specification Document from the current state as its basis.
- You must identify mutually exclusive or contradictory design, architectural design approaches in the current codebase and develop them into a coherent specification
- You must add to the specification document any mutually exclusive, contradictory or undefined instruction that may lead you to assume a decision:
  ("missing information: ...", "contradictory instructions: ...", "design decision not useful: ...")
- You should read existing workflow related documents (claude.md, session.md, tickets.md, codeql.yml, fetch-codeql-alerts.yml) and find gaps, 
- You should create a concise plan to writing the Specification document. You should persist that plan in a separate file until the Specification Document is complete
- You should include a chapter that defines terminology for terms often used interchangeably.
- You may search for relevant Specification Templates on the Internet
- You may look into the `REFLECTION` items in `SESSION.md` and look at the last commits, to get a deeper understanding of the problem.
- You may or may not follow standards to write PRD / Product Specifications.
- The document should be written in the `.md` format and should be machine readable and/or easy to parse
- You should not add any UX specifications intot the document.

The Specification Document will be written in stages (phases / aspects / chapters). Every day you should work only on exactly one aspect of the above mentioned plan per day, and keep track of aspects that are complete.

## Instructions for the use of the Specification Document

- You must enforcably check against the specification if the task, ticket, bug fix, feature implementation in the code or related documents (README.md, TICKETS) meets the specification standards before you commit / push to the repo
- Create all necessary hooks / workflows needed to guarantee fact checking mechanisms.
