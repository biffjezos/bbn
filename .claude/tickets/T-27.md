## The Problem

With every feature Claude implement, Claude hallucinates new specs, shortcuts, removes guards, couples, de-couples code modules,
changes the architecture, runs in circles, introduces errors that have been fixed weeks ago, questions or ignores previous design decisions. Claude wastes millions
by running in circles.

## Proposed Solution

For the entire project:

- its codebase (ui, middle layer, persistence),
- its infrastructure
- the interactive workflow between claude code, the project owner, ticket-, PR-, merging-, QA-management, bug reports, github actions ie. codeql, deployment)

define specifications based on the current situation and develop them into a coherent specification.

We have implicitly defined (to this date) the following:

### Programming languages

- ui: html5, javascript, css (bootstrap + bootstrap js), wasm (rust)
- middle layer services: rest, rust, crud (GET, POST, PUT, DELETE, PATCH)
- persistence: mongodb shell


### Architecture + Infrastructure

- ui: deployed to github pages, Jekyll SSG + Thymeleaf templating
- middle layer services: microservices deployed and hosted on railway.com (hobby tier)
- backend: mongodb deployed and hosted on railway.com

### Security

- Privacy-by design
- GDPR compliant (as-good-as-possible)
- data minimization (no localStorage, sessionStorage only if needed)
- encryption of all user relevant information on the backend
- E2EE, hashing, OPAQUE, JWT, ALLOWED_HOSTS

### Coding Style and Best Practices

- Modularizaton of javascript and rust libraries
- DRY, YAGNI

### Workflow

- claude.md, 
- Weekly CodeQL Analysis with Bug-Fix Session after the fetch of the analysis
  
## Instructions for the of the Specification

- You must first read this document and the this instructions and identify missing, wrong information. Only if this document is complete, specific, without errors
  you will start writing the Specification Document.
- You must develop the Specification Document from the current state as its basis.
- You must identify mutually exclusive or contradictory design, architectural design approaches in the current codebase and develop them into a coherent specification
- You must add to the specification document any mutually exclusive, contradictory or undefined instruction that may lead you to assume a decision:
  ("missing information: ...", "contradictory instructions: ...", "design decision not useful: ...")
- You should read existing workflow related documents (claude.md, session.md, tickets.md, codeql.yml, fetch-codeql-alerts.yml) and find gaps, 
- You may search for relevant Specification Templates on the Internet
- You may or may not follow standards to write PRD / Product Specifications.
- The document should be written in the `.md` format and should be machine readable and/or easy to parse
- You should not add any UX specifications intot the document.

## Instructions for the use of the Specification Document

- You must check against the specification if the task, ticket, bug fix, feature implementation in the code or related documents (README.md, TICKETS) meets about to be
meets the specification standards before you commit / push to the repo.
